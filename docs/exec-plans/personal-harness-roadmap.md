# TSAgent 个人项目发展规划（讨论草案）

日期：2026-09-09。状态：建议，尚未采纳为工程契约。

依据：本地 HEAD `65a2259c` 加当前未提交工作区、现有审计和公开项目资料。此次只做规划与静态阅读，没有修改生产代码、调用真实业务 API 或重跑验收。历史报告仅用于识别反复出现的问题类型，不代表旧 Bug 在当前版本仍然存在。开源对比是设计参考，不是实测排名。

## 1. 建议的产品定位

暂定定位：**一个理解我的项目背景、遵循我的工作方式、能交付可核对成果的个人工作助手。**

这只是待用户回答后的初始假设。优先围绕一个高频场景建立日常价值，再扩展相邻能力。候选首场景：

> “接着上次的项目，从我的笔记和仓库中找出背景，查必要资料，完成一个小任务，把产物放到指定位置，并告诉我完成了什么、还有什么没做。”

它同时检验上下文、资料检索、执行、产物与续接，能利用已有 Runtime 投入。初期由用户发起；定时主动跟进在状态与执行可靠后加入。

还需决定项目的主要回报：若偏向学习 Agent Runtime，继续自研核心有价值；若偏向尽快得到好用的个人工具，应认真评估在成熟 harness 上实现个人扩展。两者可以先用同一小场景比较投入，再做选择。

## 2. 为什么问题过去没暴露

现有材料支持的判断是：**组件正确性、公共入口接线、模型理解能力、用户目标完成度被不同测试覆盖，但它们之间缺少稳定的验收对应关系。** 这不意味着现有测试无效，而是它们证明的范围有限。

| 已有证据 | 暴露的缺口 | 对规划的影响 |
| --- | --- | --- |
| HA-R4 六条受控语义传播测试通过；报告明确不是业务完成验证 | 正确的模拟语义输入不能证明真实模型会正确理解，也不能证明最终应用可用 | 将语义、运行链路、业务交付分开验收 |
| “只展示代码、不创建文件”仍可能触发 FILE_MUTATION；实际代码合并词法与模型结果 | 不同解释机制争夺最终目标的权威 | 在目标边界统一结果和约束，删除冲突路径，不继续堆否定词特例 |
| artifact_required 是布尔值 | 无法充分表达两份报告、指定内容、运行结果等多项要求 | 在现有目标契约上表达可逐项验证的交付要求，避免另建平行目标系统 |
| Workflow checkpoint 有组件证据，但 Service resume 当前是重新接管与运行 | “实现存在”与“用户入口能用”不等价 | 明确恢复承诺，测试从公开入口进入 |
| session 原始记录、用户记忆、摘要来源与全局 repository index 存在审计债务 | 长期记忆和跨项目使用会放大上下文问题 | 个人记忆、MCP 扩展前优先收敛作用域与来源 |

证据：[目标契约审计](goal-contract-audit.md)、[HA-R4 报告](../../realtest_reports/ha_r4_gate_a/README.md)、[当前架构](../architecture.md)、[Intent 合并实现](../../agent/cognition/intent_engine.py)。

每个后续问题只记录一套信息：用户场景、最小复现、预期事实、失败层、根因、回归证据、真实验收状态。已有报告保留原始口径；建立当前问题索引引用它们，不重写历史成绩。

## 4. 建议实施顺序

按完成标准推进，不先给未经估算的日历承诺。个人项目每次只推进一个工程主题和一个用户场景。

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| A：建立可信基线 | 选择 10 条个人任务；汇总当前开放问题；校正能力声明；统一目标与约束权威 | 固定基线上的离线主路径用例通过；否定约束不产生相反动作；多项交付逐项检查；语义能力仍另列待验收 |
| B：形成个人使用闭环 | 一个主要入口；显式偏好与项目背景；清晰显示产物、已完成部分和下一步 | 同一小任务可以从请求走到可检查成果；用户不需重新交代已保存且适用的背景 |
| C：接入一个 MCP 场景 | 一个真实需要的服务器、少量工具、统一授权和结果链路 | 本地模拟服务器的发现、调用、失败、取消、隔离测试通过；真实服务器验收单独完成后才宣称可用 |
| D：长期项目协作 | 修复记忆作用域和摘要来源；可靠项目续接；按需求加入提醒 | 用户可查看、纠正、删除记忆；恢复语义明确；不会把已执行外部写操作当成未执行而盲目重做 |
| E：评估是否继续自研核心 | TSAgent 与一个成熟 harness 的同场景对比 | 能说明自研在个人体验、可控性或学习价值上的收益是否值得维护成本 |

依赖说明：B 的显式个人配置可以较早交付，但自动学习必须先解决 session/user 与摘要来源问题；C 的账号工具依赖上下文信任边界和配置作用域；D 的主动执行依赖恢复和效果记录。若长期个人助手是首要目标，就把记忆治理提前到 B。E 的小规模探索可在 A 后进行，无需等所有功能完工。

目前不优先投入分布式执行、多智能体集群、通用插件市场、全面桌面重做或复杂自动学习。只有选定场景提出明确需求时再进入范围。

## 5. MCP 接入方案

### 当前差距

依赖中有 `fastmcp` 和 `mcp`，但对 `agent/`、`tools/`、`docs/` 的静态搜索未找到生产 MCP client 接线。[ToolRegistry](../../agent/registry/tool_registry.py) 当前从 Python callable 构建工具 schema，使用模块级 registry；[product_context](../../agent/product_context.py) 主要按内建工具名生成能力说明。安装依赖不等于完成发现、调用、授权和验证。

### 首版边界

让 TSAgent 作为 host/client 使用外部 MCP 工具。向其他助手暴露 TSAgent 的 MCP server 是另一项需求，暂不与首版绑定。MCP 的 host 负责授权和上下文管理，server 提供工具、资源与提示。[官方架构](https://modelcontextprotocol.io/specification/2026-07-28/architecture)

先确定一个服务器、一个工作流、一个传输方式：本地服务可选 stdio；实际需要远程账号工具时选择其支持的 HTTP 方式和认证。先接 tools；resources/prompts 在选定工作流确实消费它们时再实现。

开始编码前锁定“服务器版本 × Python SDK 版本 × 协议版本”。截至此次查询，官方 latest 指向 2026-07-28，不能直接把旧教程的初始化与会话逻辑写成新契约。协议细节优先交给所选 SDK，确认互操作支持后使用，不自行维护猜测式兼容分支。[当前规范](https://modelcontextprotocol.io/specification/2026-07-28)、[Python SDK](https://github.com/modelcontextprotocol/python-sdk)

### 接回现有主链

拟议调用关系：

```text
AgentService / 应用上下文管理 MCP client 生命周期
  → 外部工具发现，提供明确的 schema 与服务器身份
  → 当前 workspace/account 可见的工具集合
  → 现有 Planner / Compiler / Executor 与授权
  → MCP client 调用
  → 工具结果、效果证据、Verifier
  → Store / Finalizer / 用户可见结果
```

需要处理的具体问题：

1. **注册与发现**：让内建函数和外部 schema 最终形成同一工具契约；迁移现有调用者。外部工具使用明确服务器命名空间；模型名与原始调用名保留映射，符合选定 Provider 的命名约束。
2. **配置作用域**：账号凭据与工具可见范围不能进入全局共享可变注册表；复用应用、workspace 和 run 的所有权边界。首版只实现当前个人场景实际需要的作用域。
3. **授权与上下文**：复用现有授权决策；服务器文本、工具描述、返回资料作为外部数据，不能覆盖用户目标。服务端的只读或幂等 annotations 不是独立授权依据。[工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
4. **结果与完成声明**：保留结构化结果、来源、外部对象 ID 和错误。API 返回成功只证明该调用报告成功；“用户要的内容正确写入”由对应业务检查证明。可读取的外部写入在需要时回读核对，无法确认时保留不确定状态。
5. **超时与取消**：调用超时不证明外部动作未执行；取消请求不等于远程撤销。非幂等写入结果未知时先对账，避免自动重发。连接可重建与动作可重试是不同决策。
6. **上下文成本与体验**：首版按工作流启用少量工具，显示连接状态、调用目标和结果；等真实测量显示需要时再做动态工具搜索。MCP 工具定义会增加模型上下文成本。[OpenCode 文档](https://opencode.ai/docs/mcp-servers/)

stdio 子进程也不是天然受到 TSAgent 文件沙箱约束；给它的工作目录、凭据、访问范围要与所选服务器的实际能力一起验证。首版使用合成数据，完成外部数据与授权边界后再接个人账号。

### 验收

离线使用本地受控 MCP server，从 AgentService 入口覆盖：工具列表分页、schema 传递、同名工具隔离、工具错误、连接失败、超时/取消、结构化结果、外部写入结果未知、外部文本不提升为控制指令。只测试首版支持的协议能力。

真实验收交给独立测试环境：固定服务器和模型版本、测试账号、最小权限与合成记录；执行“查找指定记录 → 汇总 → 经已有授权写入指定对象 → 回读”。核对对象 ID、内容、时间、调用与错误记录，以及取消后是否仍有远端效果。此次未执行这些真实测试。

## 6. 个人化：建议先做能减少重复劳动的内容

| 方向 | 具体体验 | 最小实现与约束 |
| --- | --- | --- |
| 工作习惯 | 默认中文、喜欢的回答长度、保存目录、编码规则 | 先用用户可编辑的显式配置；配置加载进一个权威路径 |
| 项目记忆 | “继续上次那个项目”能找到最近决定、成果和待办 | 项目记录关联来源、run 和产物；区分事实、计划、已失效结论 |
| 个人工作流 | “按我的方式整理资料”“做本周项目复盘” | 先写一两个可编辑 skill/workflow，不先建设工作流市场 |
| 可管理的长期记忆 | 能解释记忆来自哪次对话，能纠正和删除 | session 上下文、user facts、project facts 分开；摘要不可自动升级为用户事实；删除覆盖持久记录和相关缓存 |
| 主动协作 | 对已授权事项在有变化时提醒 | 在持久化和去重可靠后加入；有预算、静默条件和停止入口 |
| 角色与外观 | 名字、语气、主题、固定交付样式 | 作为独立偏好；若用户最看重陪伴与表达，可以提前，但不改变任务完成判断 |

可形成辨识度的组合是“个人项目日志 + 可追溯成果 + 熟悉的工作流”。例如每次工作结束生成一张简短项目记录：完成事项、证据、决定、下一步。是否自动保存与长期记住，由用户的明确偏好决定。

个人化也包含数据控制：本地保存的记忆不代表推理时不发送给模型服务。界面应能说明本次使用了哪些个人信息；是否需要本地模型、哪些资料不外发，待用户选择。

## 7. 如何公平比较，以及如何作出去留决定

建议先比较 TSAgent 与 Pi 或 DeepSeek Harness 中的一个，避免四套环境占用个人维护时间。Hermes 优先作为个人体验参考；若长期助手成为主目标，可改选 Hermes。

建立 10 条来自个人生活与项目的任务：3 条文件/代码交付、2 条查资料后生成产物、2 条跨轮修改或续接、2 条偏好/项目记忆、1 条已选 MCP 工作流。增加关键反例：只展示不落盘、多份交付、取消、工具失败与来源冲突。开发例和留出例分离，不能把提示中出现的原句当作泛化验收。

比较分两层：

- **尽量控制变量的比较**：固定模型完整版本、工具权限、输入数据、预算与可比能力；记录各 harness 的有效默认配置和差异。无法对齐的能力标为不适用，不偷偷补工具后混算。
- **实际使用体验比较**：允许各项目使用合适配置，比较完成效果、耗时、花费与接管次数；结论属于整套组合，不把差异全归因于 harness。

记录 Raw E2E、False Completion、约束违反次数、人工干预、耗时、tokens/费用和实际产物。Capability 按预先定义且确属外部 Provider 失败的口径排除；错误请求由 harness 造成时仍算 harness 问题。所有失败保留，定向复跑另列，不覆盖首跑成绩。小样本只作方向判断，不推导普遍排名。

再记录两个个人项目指标：“本周主动使用了几次”和“重复交代背景/手工接管减少了多少”。若修复与扩展后仍缺少可感知收益，应考虑把个人工作流迁移到成熟 harness；若可核对交付、项目记忆或学习收益明显，就保留核心并缩小支持面。
